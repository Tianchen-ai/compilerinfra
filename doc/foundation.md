# 编译器开发框架（设计讨论稿）

compilerinfra 面向开发编译器的 coding agent。它把编译器的装配、定位、修改与重新执行变成 agent 可调用的操作。输入仍然是产品真实的作者程序，留下来的成果是下一次编译会执行的代码。每个领域编译器可以独立采用这套框架。

## 加法发生在哪里

节点持有表示及其 verifier，并负责从父节点开始的 lowering。边界给出合法的停止点。产品树的父链和出口挂接点共同确定执行路线。优化贡献挂接在具名边界上。框架将这些独立声明链接成每个目标实际使用的编译过程。新增一个符合已有能力的后端，可以直接采用已有贡献；新增一个共享优化，也无需去每个相关后端修改一遍。真正需要专用算法或目标实现的工作仍归相应组件。

MLIR 已提供 pass、IR 与 verifier，LLVM 也已有 pipeline 扩展点。这里的设计取舍是让源码装配同时成为 agent 发现修改位置、查询影响范围、试换和编译的依据。是否缩短 agent 达到相同性能的时间、是否能得到更快的数值正确实现，都要通过同信息和同预算的实际比较判断。[LLVM 的 pipeline 扩展点](https://llvm.org/docs/NewPassManager.html#inserting-passes-into-default-pipelines)

## 框架与领域产品

| 责任 | 拥有者 |
| --- | --- |
| 装配检查、显式目标选择、编译会话、阶段边界、可选优化控制、诊断与产物返回 | compilerinfra |
| IR 对象、dialect、分析和 pass 的运行机制、MLIR 文本与 bytecode 格式 | MLIR |
| 输入语言、算法语义、编程模型、目标探测、编译选项、实际 lowering 与 emitter | 领域编译器 |
| 原生产物缓存、JIT 绑定、autotune、加载及 launch | 领域产品及其下游 |
| 工作负载、成熟实现、独立数值检查、运行环境、测量与输出 | 各产品的独立 Bench |

产品在自己的入口选择结构。作者语言、内部表示和下游工具链接受的输入由产品定义。框架通过调用产品交付的实现完成编译，核心代码中无需添加领域名或设备映射表。

## 优化知识怎样进入产品

一个阶段持有按实际顺序组装 pass 的代码。必须的 lowering 始终执行，允许试换的优化具有产品声明的名字。一个变换可以依赖 MLIR 的类型、访问关系、状态和设备能力，改写整个物理程序；它的生效范围由实现决定。产品接受编译器改动之后，下一次普通调用就能获得新结果。

这种组织在只交付一个 kernel 时也可能缩短搜索。改变计算与搬运的重叠方式，往往同时牵动缓冲槽、索引、等待和尾部处理。通过生成器改变这一项决定，它派生的结构会随之更新。下一位开发者可以运行留下的生成能力，替换策略，或扩大它适用的范围。是否真的优于直接生成，应在相同模型、工具和设备预算下分别比较数值正确的成品耗时和达到相同性能的开发成本。

## 为什么使用同一个入口

优化 agent 可以在产品 session 上取出真实阶段产物、替换一项优化并继续编译。Bench agent 可以从独立工具调用同一产品，对照真实机器上的完整执行。双方共享编译代码和实际输入。Bench 可以保存必要产物，开发者也可以只在内存中观察。选择哪些案例、何时计时和如何判定正确由 Bench 负责。小改动由一位开发者即可完成。

## 稳定边界

链接确定一台编译器。派生以这台编译器为父对象，返回保有完整接口的新定义。每个已打开的 session 持有自己的定义，产品目标、数值设置和策略链归该定义所有。源码插件可以交付实现、动作、skill 或服务。开发作用域负责它们的安装与撤回，独立 Bench 负责实际输入与裁判。

当两项决定必须联合才合法时，领域 family 在实际 IR 上接受一个完整的值。例如工作集预算同时制约分块和流水深度，策略一次提交整组取舍，realizer 据此产生索引、缓冲和等待。相容目标可绑定同一能力接口，不同策略和不同兑现者可以分别贡献。框架长期维护的是这套链接、派生、作用域和编译语义。[完整接口](derivation.md)

产品以源码组件扩展框架。新增目标、更新资源模型或替换局部优化在子仓装配。MLIR SDK 与产品一起构建或链接，公共 API 使用原生 MLIR 类型。跨工具链的独立二进制插件 ABI 属于另一项设计。母仓的 API 和源码是当前交付，领域编译器的迁移、性能保持以及 agent 开发效率仍有待实际使用验证。
